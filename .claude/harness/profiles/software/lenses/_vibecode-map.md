## Phase 1 — Reconnaissance and mapping

In the main session, with no subagent. Goal: know *where to look*, not to audit.

1. **Arguments, git, resume**: write `$ARGUMENTS` as is to `.harness/runs/vibecode-audit-arguments.txt`, then `K audit start --skill vibecode-audit --arguments-file …` (AU-01 to AU-03, VA-01, VA-02: absolute `REPO`; `--axes` among `securite`, `maintenabilite`, `evolutivite` separated by `;`; `--max-findings` capped at `min(N, 30)` default 15; nonexistent path → stop, invalid value → exit 2). **Removing `securite` requires confirmation**: gate `vibecode-audit.drop-security` (*confirm the removal* / *keep*), before `start`. The core probes git (`git_absent`: pre-finding to report, **no git command afterwards**), resumes an existing `AUDIT-vibecode.md` (AU-09: `FAIT`/`EN_COURS` statuses preserved, `VIB-` numbering continued, never comparing the two states) and returns `run`, `auditors` (model and `pass_param`: pass `model` to the Agent tool when `pass_param` is true, never for `inherit`), `validator`, `cap`.
2. **Project shape**: `K stack detect --root "<REPO>"`; 2-3 level tree; dependency manifests and lockfiles, client / server / asynchronous split, data schema and migrations, tests, CI, per-environment configuration.
3. **Trust boundaries**: locate the exposed entry points (routes, controllers, request-triggered functions, event handlers) and the data access layer — the map that `acces`, `injection` and `metier` receive.
4. **Generation signals** (noted, never held against): large and few commits, heterogeneous styles between neighboring files, comments paraphrasing the code, instruction files for an assistant, gaps in a numbered sequence. **Systematic search for reimplementation candidates**: same-level directories with close names (same root, singular/plural, added suffix) and files with the same name in different directories; each pair enters the `maintenabilite` map with an instruction to compare it. This is the most characteristic pattern of vibecoded code and the only one that no auditor finds file by file.
5. **Deterministic checks**: the package manager's vulnerability audit and a secret detector, if they exist, read-only and without installing or updating; **tool absent → unauditable surface**. Sort the vulnerabilities **by reachability in production** before any aggregation.
6. **Distribution artefact**: if the project produces a client deliverable (package, bundle, image), check what it contains; unavailable without building the project (which this skill does not do) → unauditable surface (secrets exposed client-side are not visible in the sources).
7. **Bounds**: `sampled` returned by `stack detect` beyond 2000 files: 3-level tree, 40 files read per auditor, sampling on the exposed entry points, the data access layer and the largest files.

Produce the **map**: shape, trust boundaries, tests / CI / migrations / configuration, generation signals, deterministic checks, unauditable surfaces, `git_absent`, resume, sampling.

Status: APPROVED

# SPEC-leg-26 — Host bench: ELF validation tests, malformed-ELF corpus and fuzz target

## Context

Enabler LEG-26 (milestone 0), depends on LEG-25, prerequisite of the LEG-01/02/03 hardening.

Once the ELF parser is extracted into a pure unit (LEG-25), it becomes host-testable. This spec
builds the net that will make the hardening verifiable instead of taken on trust.

The bench already exists and is not to be created: `tests/host/Makefile` compiles three tests
(`test_re`, `test_i2c_decode`, `test_known_yaml`) with `gcc -std=c17 -Wall -Wextra -Werror`, runs
them through the `test` target while propagating the exit code, and the CI job `Run host unit tests`
in `.github/workflows/ci.yml` already runs `make -C tests/host test`. The assertion harness is
`tests/host/tassert.h`.

The malformed-ELF corpus is the missing piece: it is what will turn the LEG-01/02/03 acceptance
criteria into executable checks rather than code review.

## Scope

Add to the host bench a unit test for ELF validation, a generated malformed-ELF corpus, and a
fuzzing target; wire all of it into the existing `Makefile` and CI job.

## Acceptance criteria

1. A host test (for example `tests/host/test_elf_validate.c`) exercises the pure unit extracted by
   LEG-25, driving it from in-memory buffers, with no filesystem access.
2. The corpus covers at least the following cases, each being an otherwise well-formed ELF so as to
   isolate the defect under test: `e_shstrndx >= e_shnum`; `sh_link >= e_shnum`; `sh_name` beyond
   the size of the section string table; `st_name` beyond the symbol string table; oversized
   `e_shnum` (beyond `MAX_SECTIONS`); `sh_offset` + `sh_size` overflowing the file size; zero
   `sh_size` on a table expected to be non-empty; `e_shoff` beyond end of file; file truncated in
   the middle of the section header table.
3. Every corpus case carries an assertion on the **expected return code**, not merely on the absence
   of a crash: a test that would pass because the program did not crash does not satisfy this
   criterion.
4. The corpus is **generated by versioned code** (C or Python generator) rather than stored as
   opaque binaries, so that each case is readable and modifiable; if binaries are committed anyway,
   the generator that produces them is committed too.
5. At least one **valid** ELF is part of the corpus and is accepted: the suite must prove it does
   not reject everything indiscriminately.
6. The new tests are added to the `TESTS` variable of `tests/host/Makefile`, and
   `make -C tests/host test` compiles them, runs them, and returns a non-zero exit code if any of
   them fails.
7. A fuzzing target (`make -C tests/host fuzz` or equivalent) builds a libFuzzer or AFL binary
   exercising the ELF validation entry point, seeded with the criterion 2 corpus.
8. The existing CI job runs the new unit tests with no change to its command
   (`make -C tests/host test`), and a **time-bounded** fuzzing run is added to CI, with an
   explicitly defined duration and crash-handling behaviour.
9. On the current commit, before any hardening, the suite runs and **documents actual behaviour**:
   the cases the loader does not yet reject are marked as expected failures (or equivalent), so that
   turning green is exactly the evidence produced by LEG-01/02/03. CI must not be red because of
   already-known, already-planned bugs.

## Out of scope

Fixing the revealed bugs (that is LEG-01/02/03); tests of the relocation engine, symbol resolution
or manifest parsing; fuzzing other components; coverage measurement; integrating a continuous
fuzzing service; QEMU tests (handled by LEG-27).

## Risks

Criterion 9 is the delicate point: writing a suite that fails outright on the current commit would
turn CI red and encourage working around it. The expected-failure mechanism must be explicit and
temporary, and must be removed by LEG-01/02/03 — otherwise it becomes a permanent mask.

Fuzzing in CI costs time and can be flaky: criterion 8 requires a duration bound and a written
decision on what happens when a crash is detected, to avoid a job that fails at random and ends up
ignored.

## Open questions

None

## Implementation decisions (recorded during the build)

1. **Crash isolation.** Some corpus cases read out of bounds today rather than returning an error
   (ASan reports the faulting read at `elf_parse.c:76`, where `ss->sh_size` is dereferenced through
   the out-of-range `shdrs[e_shstrndx]` address formed on the preceding line), which aborts under
   ASan. Each case therefore runs in a forked child; the driver turns a signal or a non-zero exit
   into an observation instead of losing the suite.
2. **Expected-failure mechanism.** Markers live in the `xfail_owner` field of
   `tests/host/elf_corpus.c` and name the finding that must delete them (`LEG-01`, `LEG-02`,
   `LEG-03`). Those three are **findings inside one approved spec**,
   `specs/SPEC-leg-01-harden-elf-validation.md` — not three specs; its criterion 1 removes all four
   `LEG-*` markers in a single change. A marked case that starts passing is reported as `XPASS` and
   **fails the suite**, so a stale marker turns CI red and cannot become a permanent mask. The
   number of expected failures is printed on every run.
3. **How much a case may assert about the reject reason.** The `why_mode` field is a three-state
   choice, and the third state exists to keep the XPASS mechanism live. `WHY_EXACT` demands a named
   `duneos_elf_reject_t`; `WHY_ANY` demands only that a rejection carry some reason.
   `WHY_UNOBSERVED` is for the two LEG-03 cases, whose defect is reached through a string accessor
   *after* `duneos_elf_image_open()` has already returned 0: `why` is structurally
   `DUNEOS_ELF_REJ_NONE` there and says nothing about the accessor — for `st_name_past_strtab`
   unconditionally so, since the symbol string table is read from raw bytes outside the image.
   Demanding a reason on those cases would keep them failing after the defect is fixed, so the
   marker could never flip to `XPASS` and the fix would land unreported — exactly the permanent mask
   the Risks section forbids. For them the return code is the whole assertion (criterion 3), and it
   is precisely what changes when they are fixed.
4. **Defects outside SPEC-leg-01.** Two criterion-2 cases (`sh_offset + sh_size` overflow, zero
   `sh_size` on a table expected non-empty) are not covered by any approved spec. Neither can be
   converted by SPEC-leg-01 as written: `duneos_elf_image_open()` never inspects a non-shstrtab
   section's extent and `duneos_elf_io_t` carries no file size, so the unit under test structurally
   cannot produce the expected rejection without an API change. That is stated in each case's
   `defect` string, and each carries a tracked owner — `UNPLANNED:BL-ELF-EXTENT` and
   `UNPLANNED:BL-ELF-EMPTY-SYMTAB`, matching the two `docs/backlog.md` entries that own them — so
   the markers have a home instead of rotting. They are counted separately in the test output rather
   than silently attributed to LEG-01/02/03.
5. **Fuzzing in CI.** Separate `fuzz-elf` job, 120 s bound with a 25 s per-input timeout; crash
   reproducers are uploaded as an artifact. The job is `continue-on-error` **only** while the
   LEG-01/02/03 defects stand — SPEC-leg-01 criterion 4 removes that flag. Because
   `continue-on-error` would also hide a runner with no clang, a second step that is **not**
   `continue-on-error` asserts the `fuzz_elf_validate` binary exists and that the run reached its
   completion marker, so "ran clean" is distinguishable from "never built".

# ADR 040 — Project policy vs. board measurement: where a Kconfig value belongs

**Status:** Proposed · 2026-09-06

## Context

DuneOS has two places a Kconfig symbol can be set, and until now no rule saying which:

- `sdkconfig.defaults` at the repo root — read for **every** board.
- `boards/<board>/sdkconfig.board` — generated by `duneos-bspgen.py` from that board's `board.yaml`.

The absence of a rule cost a working board. Merging LEG-25/27/28/29/01 turned a booting M5Stack CardPuter into a reboot loop. `main_task` runs the entire boot on ESP-IDF's 3584 B default stack — mount LittleFS, mount SD, then `duneos_loader_scan` over every `.dap` in `/bin`, a chain that descends `lfs_bd_crc → lfs_bd_read → esp_partition_read → spi_flash_op_lock`. LEG-25's parser extraction added one struct local and one call frame on exactly that path, and on Xtensa's windowed ABI a frame spills a register window. Measured on the hardware with the stack temporarily raised to 12288 B so the measurement could not itself overflow, `uxTaskGetStackHighWaterMark(NULL)` reported 8524 B free — a peak of **3764 B against a 3584 B default**. The board was overflowing by 180 bytes.

The obvious fix — raise `CONFIG_ESP_MAIN_TASK_STACK_SIZE` in `sdkconfig.defaults` — is the wrong one, and the reason generalises well past this symbol.

**A stack watermark is a property of (architecture × that board's boot workload).** Xtensa spills a register window per call frame; RISC-V does not, so `esp32c3` will not need the same figure and may well fit the default. A board with `has_sd: false` never walks the `sdspi` mount path at all. Declaring one board's measured peak at the root makes all eight boards pay the maximum of whichever board happened to be measured — and the seven that were not measured get a number that describes none of them.

**It is also an ESP-IDF artefact.** `CONFIG_ESP_MAIN_TASK_STACK_SIZE` is a symbol of one SDK. RP2040 has no `sdkconfig` at all. A value written as a raw Kconfig line is untranslatable; a value written as *intent* in `board.yaml` is exactly what a second SDK's generator needs.

The counter-example in the same change is what makes the rule worth writing down. `CONFIG_FREERTOS_WATCHPOINT_END_OF_STACK` is what turned this bug from expensive to trivial. Without it the overflow ran into the adjacent heap: TLSF's free list took stack contents (return addresses where the free poison `0xfefefefe` belonged) and the crash surfaced thousands of instructions later inside an unrelated `malloc`, at a different place on each boot — once in cJSON under `extract_manifest`, once during the SD mount. Heap poisoning reported `CORRUPT HEAP` with no culprit. With the watchpoint, an overflow that writes into the watched region is a `Guru Meditation Error … Stack canary watchpoint triggered (main)` naming the task, instead of a `CORRUPT HEAP` naming nothing.

It is a diagnostic, not a proof, and it is not free. ESP-IDF's Kconfig help for the symbol states both limits:

> This check only triggers if the stack overflow writes within 32 bytes near the end of the stack, rather than overshooting further, so it is worth combining this approach with one of the other stack overflow check methods.

> Another consequence is that due to alignment requirements of the watchpoint, the usable stack size decreases by up to 60 bytes.

A single Xtensa register-window spill is 16–64 bytes, so one deep call frame can step clean over the watched 32 bytes and land in the heap exactly as before — the canary and the watchpoint are a **pair**, catching different overshoot distances at different moments, and neither alone closes the failure mode. The 60-byte cost also lands on every task on every board, including the seven still on the unmeasured 3584 B default: enabling it moves them slightly *closer* to the overflow it diagnoses. That trade is taken deliberately (a named panic is minutes, a heap bisect on hardware was days), but it is a trade, not a freebie.

What makes the symbol project-wide is none of that. It is **not** a measurement of any board: it is a statement about how this project wants to fail, and there is no board that wants its overflows silent.

Same file, same change, opposite homes. The distinction is the content of this ADR.

## Decision

**The board declares intent; the generator translates it per SDK.** This is [ADR 015](015-declarative-driven-architecture.md)'s pattern applied to Kconfig, and the test for where a value belongs is one question:

> Is this value a fact *measured on, or wired into, one board* — or a decision about how the project behaves everywhere?

- **A per-board MEASUREMENT** — the answer to "how deep does this board's boot actually go", "how much flash is soldered on", "which console pin exists" — is a **typed key in `board.yaml`**, validated by `duneos-bspgen.py`, emitted into that board's `sdkconfig.board`. Omitting the key emits nothing and leaves the SDK's own default in force; the generator never writes a default it invented, because doing so freezes that default against an SDK upgrade.
- **A project-wide POLICY** — diagnostics, error behaviour, the failure mode we want, anything a new board would want on day one without being measured — belongs in **the SDK's project-wide defaults file**, with a comment saying why it is not per board. Under ESP-IDF that file is `sdkconfig.defaults`.

Both halves have to survive a second SDK, and only the first is portable by construction. `sdkconfig.defaults` is itself an ESP-IDF artefact: a Pico-SDK or host port has no such file, so "put it in `sdkconfig.defaults`" is not yet a rule, it is one SDK's spelling of one. The rule is:

> A POLICY is stated once, in whatever single artefact that SDK reads for **every** board, and it is stated in the SDK's own vocabulary. It is never spread across the board files.

For ESP-IDF that artefact exists and is `sdkconfig.defaults`. For an SDK that has no project-wide config file, the port creates the one destination — a shared `duneos_policy.cmake` fragment, a common compile-definitions block, whatever that SDK reads before the per-board build — and it is a defect in the port if a policy has to be repeated per board to take effect. What must never happen is a policy landing in `board.yaml`: that would make every future board silently opt out of it by omission, which is the opposite of what a policy is for.

`main_task_stack: N` is the first typed key added under this rule (SPEC-leg-37): bspgen validates it as a positive, 4-byte-aligned integer and rejects anything else naming the board and the offending value, rather than coercing it. `CONFIG_FREERTOS_WATCHPOINT_END_OF_STACK=y` goes to the root under the same rule.

**A typed key is preferred to the raw `kconfig:` passthrough.** `board.yaml` already accepts a `kconfig:` list emitted verbatim — the escape hatch for tuning bspgen does not model. It is unvalidated, undocumented and SDK-locked, so it is the place a value lands *before* it earns a key, not its destination. `boards/kincony-A16` sets `CONFIG_ESP_MAIN_TASK_STACK_SIZE=8192` that way today, predating this key; converting it needs a measurement nobody has taken. Because the passthrough is emitted last, a raw entry would silently outrank a typed key for the same symbol — bspgen now refuses that collision outright rather than picking a winner.

**Surviving a second SDK.** `main_task_stack: 4608` says *this board's boot needs 4608 bytes*, which is true regardless of who compiles it. The ESP-IDF generator turns it into `CONFIG_ESP_MAIN_TASK_STACK_SIZE=4608`; a Pico-SDK generator would size its own main stack from the same key; a host build could ignore it. Had the number been written into `sdkconfig.defaults` — or into the raw `kconfig:` list — the port would have inherited a symbol with no meaning and a measurement with no owner.

**A measurement must carry its derivation.** A bare number is indistinguishable from a guess, and the next person to hit a stack overflow cannot tell whether the value was measured, inherited, or picked. The comment beside the key records the method, the date, the conditions, and the margin — see `boards/m5stack-cardputer/board.yaml`.

## Consequences

- Each board's Kconfig fragment describes that board and nothing else. One board (`m5stack-cardputer`) declares a measured stack; six keep ESP-IDF's 3584 B default because nothing was measured on them; `kincony-A16` is on neither — it sits on an unmeasured **8192** through the raw `kconfig:` passthrough, a number with no recorded derivation and no owner. That is honest rather than convenient.
- **Seven boards remain a known gap, and they are not all the same gap.** The six on 3584 B are one call frame from the CardPuter's failure and nothing in this rule tells us which. `kincony-A16` is the more interesting one: someone already hit this, raised the stack to 8192, and left no trace of why or of what they measured — the untraceable workaround this ADR exists to stop being the normal outcome. Converting it to the typed key needs a measurement nobody has taken. The gaps are recorded deliberately instead of being closed by raising the default for everyone — that would trade a visible gap for an invisible cost on every board.
- The gap is more survivable *because* of the policy half: the root watchpoint makes an overflow that writes into the last 32 bytes a named panic on whichever board hits it, instead of heap corruption found by bisect on hardware. It does not make a wrong margin safe — an overshoot past the watched region still lands in the heap, and the watchpoint costs up to 60 B of the very stack it is watching. This is why the two halves ship together, and why neither is a substitute for measuring.
- **Layering only holds if the build honours it.** ESP-IDF applies an `SDKCONFIG_DEFAULTS` entry only to a symbol not already present in a build directory's cached `sdkconfig`, so a build dir configured before either layer changed keeps its old values, reconfigures with exit 0, and flashes them — the declaration is read and discarded in silence. That is this same bug one layer up, and it was armed in the tree the moment the CardPuter's value changed. `tools/dbt/sdkconfig_check.py` compares both declared layers against the cached config before a build or flash and refuses on a contradiction, naming the symbol, both values and the remedy. A symbol absent from the build config is not a contradiction — Kconfig legitimately drops one whose dependencies are unmet.
- **An unrecognised `board.yaml` key is now an error.** A typed key is only as safe as the parser's willingness to say it did not understand: `main_task_stac: 4608` generated cleanly, emitted no symbol, and left the board on the default that bricks it. `duneos-bspgen.py` validates top-level keys against a whitelist and suggests the near miss. The cost is that a board declaring hardware no generator models yet must still be listed — `lora`/`rfid` on lilygo are in the whitelist for exactly that reason.
- Every new tuning value now needs a decision — measurement or policy — before it is written. That is one more question at review time and the point of the ADR.
- Adding a typed key costs a validated branch in `duneos-bspgen.py` plus tests. The raw `kconfig:` list stays available for values that have not earned that, and stays the weaker option on purpose.

## Alternatives

- **Raise `CONFIG_ESP_MAIN_TASK_STACK_SIZE` in `sdkconfig.defaults`** — rejected. One line, immediately unblocking, and it makes every board pay one board's Xtensa-shaped maximum while attributing a measurement to seven boards it was not taken on. It also puts an ESP-IDF symbol where a non-ESP-IDF port must reinterpret it.
- **Put the watchpoint in each board's `board.yaml` too, for symmetry** — rejected. It is not a property of any board — its up-to-60-byte cost falls on every task on every board equally, which is what a policy looks like — and per-board placement means a new board silently opts out of the one diagnostic that made this bug findable.
- **Raw `kconfig:` entry on the CardPuter** — rejected as the destination, though it is where such values legitimately start. No validation (a non-aligned or negative value would reach the build), no documented schema, and the string is an ESP-IDF symbol a second SDK cannot translate.
- **Measure all eight boards now and declare each** — not rejected on merit, deferred on cost: seven of them require hardware on the desk. The rule is what makes the deferral safe to record.
- **Size the stack at runtime, or move the loader scan onto its own task** — out of scope here. The scan on a dedicated task costs a whole additional task stack to save ~1 KB on one board, and neither changes where a declared value belongs.

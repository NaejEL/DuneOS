# ADR 015 — Declarative-driven kernel/userspace architecture

**Status:** Accepted · 2026-05-20

## Context

ADRs 009 (kernel/userspace boundary), 010 (architecture accelerators), and 014 (capability resolution) each addressed a slice of "where does code live, and how does it find its peers?" — but they left three structural debts unaddressed:

1. **Kernel-side driver registry is hand-maintained.** `kernel/duneos_kernel/src/vfs_dev.c` contains an exhaustive list of `#ifdef CONFIG_DUNEOS_DRV_X / extern void drv_X_register(void) / drv_X_register()` triples. Adding a new chip driver edits four files (Kconfig, CMakeLists, two sites in vfs_dev.c). The kernel "knows" all possible drivers by name, even ones a given board doesn't use. The list will only grow.

2. **Userspace device paths are hardcoded.** `libdisp.c` opens `/dev/disp0` literally. `libst7789.c` parses `/flash/board.info` at runtime to find a SPI host. If a board wires its ST7789 on a different bus, the SDK source must be edited — or a runtime parser added. Either way, the build-time knowledge in `board.yaml` is rediscovered at runtime, badly.

3. **Chip drivers live in the kernel.** Even with ADR 009's matrix in place, "user adds a board with display X" requires kernel changes (new `drv_disp_X.c`, Kconfig option, etc.). The kernel binary risks bloating with chip-specific code for every board the project ever supports. The right end-state is **chip drivers as userspace `.dap`s**, registered through a uinput-style mechanism. The kernel keeps only bus controllers, scheduling, VFS, and the loader.

These are not separate problems — they share a root cause: **the system pretends to be configuration-driven but actually requires code edits at every level**. The board.yaml is the source of truth on paper, but in practice it's a fragment that the rest of the system re-encodes by hand.

## Decision

DuneOS commits to a **declarative-driven architecture** with three concrete patterns:

### Pattern 1 — Driver self-registration (kernel-side)

Drivers register themselves at link time via a dedicated ELF section. The kernel iterates the section at boot. The list of drivers in `vfs_dev.c` disappears.

```c
// kernel/duneos_kernel/include/duneos/driver_init.h
typedef int (*duneos_driver_init_fn_t)(void);

#define DUNEOS_DRIVER_REGISTER(fn) \
    static const duneos_driver_init_fn_t _duneos_drv_##fn \
        __attribute__((section(".duneos_driver_init"), used)) = fn

// In each kernel/duneos_kernel/src/drivers/drv_xxx.c:
static int drv_xxx_register(void) { /* devfs_register, klog, … */ return 0; }
DUNEOS_DRIVER_REGISTER(drv_xxx_register);
```

`vfs_dev.c` becomes generic — no `#ifdef`, no `extern`, no per-driver line. It just walks `__duneos_drivers_start..__duneos_drivers_end` (defined by the linker script). Kconfig still gates the compilation of each `.c` (so disabled drivers contribute nothing to the section), but the kernel core stops needing to know names. **Adding a kernel driver = drop a `.c` in `drivers/`, add one Kconfig option, add one `if(CONFIG_…)` in CMakeLists.txt. Zero edit to vfs_dev.c.**

Implementation in Phase 24.9 (see ROADMAP).

### Pattern 2 — Userspace `<duneos/board.h>` auto-generated by dbt

`dbt build` emits a per-app header `_board.h` in the build directory, populated from the active `board.yaml` plus the app's declared capabilities. Apps include `<duneos/board.h>` (alias to that file) and use defines instead of literals. **The board.yaml is read once at build time, never re-parsed at runtime.**

```c
// build/g_shell/_board.h (auto-generated, do not edit)
#pragma once
// Generated for board: m5stack-cardputer @ 2026-05-20T14:30Z

#define DUNEOS_BOARD_NAME        "m5stack-cardputer"
#define DUNEOS_DISPLAY_DEV       "/dev/disp0"
#define DUNEOS_DISPLAY_WIDTH     240
#define DUNEOS_DISPLAY_HEIGHT    135
#define DUNEOS_INPUT_DEV         "/dev/input/event0"
#define DUNEOS_HAS_SD            1
```

Apps and SDK libs (`libdisp.c`, `libgfx.c`, `libst7789.c`, …) stop hardcoding `/dev/disp0` or parsing `board.info`. **Moving the ST7789 from SPI3 (kernel-owned, `/dev/disp0`) to SPI1 (userspace-exposed, `/dev/spi-1`) becomes a board.yaml edit — the regenerated `_board.h` carries the right device path, every consumer adapts automatically.**

`/flash/board.info` stays — it's useful for runtime introspection (a debugger app, ifconfig-style tools) and for apps loaded from external SD without a custom build. But it's no longer the primary configuration channel.

Implementation in Phase 24.8 (see ROADMAP).

### Pattern 3 — Chip drivers as userspace apps (north star, post-Phase 29)

The end-state: the kernel ships with **only** bus controllers (UART, I2C, SPI, GPIO), the VFS, the loader, the supervisor, and `duneos_osal`. Every chip-specific driver — display, sensors, GPIO expanders, peripherals — lives as a `.dap` in `apps/system/drivers/`. They open the relevant `/dev/spi-N` / `/dev/i2c-N` / `/dev/gpiochipN`, expose their own device through a uinput-style mechanism (`/dev/devfs_create` or similar), and the supervisor restarts them on failure.

This is what Linux did with the user-mode driver framework (UIO, libusb, FUSE). It's not appropriate today because:

- DuneOS doesn't yet have uinput / devfs-from-userspace
- Driver authority and signing (ADR 011) need to be tightened before letting arbitrary `.dap`s register devices
- Performance impact of going through VFS for every register access vs direct memory map is unmeasured

The north star justifies decisions made today (e.g. always exposing buses to userspace), but no phase commits to delivering it before Phase 29 (RP2040 port). It is the **direction**, not the **deadline**.

## Consequences

- **Boards become declarative for real.** Today's `board.yaml` already declares pin counts, freq, MADCTL, etc. After Phase 24.8 + 24.9, it becomes the *only* place a board is described. Adding "this board uses display ILI9341 on /dev/spi-2" requires: (a) one line in `board.yaml`, (b) shipping `sdk/display/libili9341.c`. Zero kernel touch, zero app touch.

- **Kernel surface shrinks over time.** Pattern 1 makes the kernel's driver list self-managed; Pattern 3 (long-term) moves the drivers themselves out. The kernel binary footprint becomes a function of how many chip drivers a *board* needs, not how many *DuneOS supports*.

- **App portability matches its promise.** ADR 014 promised "same source, any board"; today that's only true for capabilities resolved at build time (one chip lib per app). After Phase 24.8, even the device paths come from board.yaml, so libraries that use `DUNEOS_DISPLAY_DEV` don't care what bus the chip is on.

- **Implementation complexity is concentrated in dbt.** dbt becomes the build-time orchestrator: reads board.yaml, generates _board.h, picks capability sources, drives the kernel build. Apps and the kernel each stay simple. This is consistent with the project's "DX First" manifesto — complexity goes into tooling, away from users.

- **Pattern 1 has a linker-script dependency.** The kernel's linker script must define `__duneos_drivers_start` and `__duneos_drivers_end` symbols around the `.duneos_driver_init` section. On ESP-IDF, this means a custom section in `sections.ld.in`. On future SDKs (pico-sdk, etc.), the same pattern applies but the linker script lives elsewhere. The `arch.cmake` is the right place to inject this.

- **Pattern 2 has a watch-mode concern.** `_board.h` is generated; if `board.yaml` changes after the app is built, the app must rebuild. `dbt build` should treat `boards/<active>/board.yaml` as a dependency of every `.o` (CMake-style depfile, or a "touch the build dir" trigger when the active board changes).

- **Pattern 3 is what Phase 25 (`dbt system`) starts unlocking.** `dbt system` already plans to validate apps against a kernel profile; the same machinery extends to "this driver app is part of the system image." A future "Phase 3x — Userspace driver model" turns the north star into a real phase when the pieces are ready.

## Alternatives

- **Stay imperative (status quo)** — rejected. Every new board / chip multiplies the editing required across vfs_dev.c, CMakeLists.txt, app manifests, and SDK libraries. The cost of supporting one more board exceeds the value it brings.

- **Pattern 1 via Kconfig generation only** (a generated `vfs_dev_driver_list.h`) — rejected. Still requires editing one file (the generator config), and `vfs_dev.c` still names every driver via `#include`. Self-registration via ELF section is the established pattern (Linux, FreeRTOS-Plus, …) and adds no runtime overhead.

- **Pattern 2 via runtime `board.info` parsing** (current state) — rejected as the long-term solution. Parsing YAML in a `.dap` that wants to draw a pixel is wasteful when dbt already knows everything at build time. Runtime board.info stays as a debugging surface, not as the primary config channel.

- **Pattern 3 immediately** (drivers as userspace apps now) — rejected. The infrastructure (uinput, signing, driver host) isn't ready. Charging at this target before Phase 25 / Phase 29 means committing to a moving goalpost.

- **Single mega-phase that does all three** — rejected. Each pattern has independent value and can ship independently. Bundling them creates a 4-week monster phase that's easier to abandon. Two crisp 1-week phases (24.8 + 24.9) plus a long-term north star is healthier.

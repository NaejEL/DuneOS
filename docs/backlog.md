# DuneOS — backlog

A holding pen for ideas and gaps that surfaced during planning but aren't on the roadmap yet. Not a commitment; a memory aid. Move an item to `ROADMAP_v2.md` or a new ADR once you decide to do it.

Items are grouped by impact, not by phase. Each line is one sentence — if it grows, it's probably ready to become a roadmap entry.

---

## High impact (likely to be scheduled later)

- **Kernel self-defense, round 2** — the two historical "userspace wedges the kernel" bugs (crash-storm TCB reuse on `xTasksWaitingTermination`; devfs fd-pool leak on app death) were root-caused, fixed and **hardware-validated 2026-07-26** (suspend+delete exit protocol in `supervisor.c`; per-slot `fd_mask` reclaim wired into both syscall surfaces — see commits `f343e13`). What remains of the only promise an MMU-less OS can make: (1) fds opened from an app's **pthread children** aren't tracked (child tasks have no slot); (2) no per-app fd quota — one app can still hold all 32 devfs slots; (3) stack canaries still pending (Phase 20 🟡); (4) the software WDT cannot interrupt an app blocked inside a kernel syscall; (5) **everything is pinned to Core 0** — half the chip idles to dodge SMP list races instead of fixing them. (5) is acknowledged debt with a due date: Phase 26 (OSAL) must actually pay it, not carry it forward.
- **CI / automated verification — the #1 structural gap** (in progress 2026-07-26). 12 k LOC of kernel, 42 apps, zero tests, zero CI: every regression is caught by eyeball on hardware (proof: the wifi_daemon eager-init boot OOM shipped through build+review and was caught on-screen). Bootstrap order: (a) host-side unit tests for the pure-C modules — `sdk/re` regex engine, `sdk/proto/i2c_decode`, the known.yaml grammar (three hand-rolled copies today — extract ONE shared parser into sdk/, that duplication is itself a bug factory); (b) GitHub Actions: host tests + kernel build (espressif/idf docker, bspgen + idf.py) + `dbt system build`; (c) later: QEMU-S3 boot smoke running `selftest.sh`; (d) `dbt build` should verify an app's undefined symbols against `symbols.c` at build time instead of failing at load time on device.
- **`/data` user partition — user state must survive a reflash** (in progress 2026-07-26). `dbt system flash` regenerates the whole `/flash` LittleFS image: known.yaml, scores, prefs are wiped on every firmware update — a product-killer for the drag-and-drop-handheld pitch, and the prerequisite for any OTA story. The 5.4 MB `storage` FAT partition bspgen emits is mounted by NOTHING in the kernel — repurpose it as a `userdata` LittleFS partition mounted at `/data` (format-on-first-mount, non-fatal if absent). Then: wifi known.yaml moves to `/data/wifi/known.yaml` (with `/flash/etc/wifi/known.yaml` as read-only board-provisioned fallback), and the backlog item "App writable state" resolves to the `/data/<app>/` convention.
- **OTA / kernel update story** — today the kernel is updated via `dbt flash kernel` (USB UART/JTAG); no A/B partitions, no in-system updater, no WiFi push. Blocks non-dev adoption. Likely a phase of its own once Phase 25 (`dbt system`) ships, because `dbt system deploy` is the natural carrier.
- **Persistent coredumps in `/flash/crash/`** — today `klog` is a 4 KiB RAM ring buffer lost at reboot, and the supervisor exception handler dumps via `esp_rom_printf` (visible only if console is connected). ESP-IDF has `esp_core_dump` that targets a dedicated partition; could be wired in. Could absorb into Phase 20 (Memory hardening), which is already 🟡 PARTIAL.
- **App debugging story** — JTAG via VS Code ESP-IDF works for kernel devs, but app authors get hex register dumps when their `.dap` crashes. Symbolic stack trace (using `addr2line` against the `.elf` left on disk by `dbt build`) would be a big DX win. Could be a `dbt trace <coredump.bin>` subcommand. Depends on persistent coredumps existing first.
- **Captured-bin stack guard — a captured app must not be able to reboot the system.** Captured bins (`ls`/`cat`/`grep`…) run *on the shell's stack* (ADR 016, same task), so a tool with large locals reached through a deep chain (a pipeline: `run_pipeline`→`run_stage`→loader→tool→VFS-write-sink) can overflow the shell stack and corrupt *adjacent* memory before any check fires — observed 2026-06-13 as a **full ESP reboot** on `cat … | grep` (grep's ~1.6 KB `grep_fd` frame over the pipe chain past an 8 KB shell stack). **Mitigated 2026-06-14 (option 2 implemented):** the loader now measures the
*current* free stack (`vTaskGetInfo` → `pxStackBase` vs live SP) before every
captured run and **refuses with `-ENOMEM`** when it's below `CAPTURED_MIN_STACK`
(4 KB), so an over-deep `source`/pipeline gets a graceful "not enough stack"
instead of a reboot. Shell stack also raised to 20 KB and grep/sed locals
trimmed. Remaining (nice-to-have, not urgent): (1) a **dedicated guarded stack**
for captured bins (true isolation; needs a stack switch) or `configCHECK_FOR_STACKOVERFLOW=2`;
(3) per-run sacrificial region. The hard-reboot path is closed; this is now about
robustness margin, not a live hazard.
- **SSH server (encrypted network shell) — PSRAM-gated.** `telnet_shell` (cleartext, ADR 011 advisory model) is the no-PSRAM answer; SSH is the secure upgrade for boards that can afford it. Cost: key exchange + ciphers + MACs (wolfSSH/libssh over mbedTLS — mbedTLS is already pulled in by WiFi) ⇒ ~20-40 KiB RAM per session + flash + CPU, infeasible on the ~50-80 KiB free heap of the no-PSRAM CardPuter. On a PSRAM board it fits: a new `ssh_shell` backend would be ~the same thinness as `telnet_shell` (accept → handshake → `shell_run(channel_fd)`) once a crypto-channel fd wrapper exists. Gate it like [ADR 035](adr/035-micropython-app.md) via the app-`requires`/board capability check (next item). Worth an ADR when scheduled.
- **MicroPython as a PSRAM-gated `.dap` app** — see [ADR 035](adr/035-micropython-app.md) (Proposed). Ship the MicroPython VM as a regular DuneOS app (large `heap_size` served from the PSRAM arena), board-gated to PSRAM targets via the capability system ([ADR 014](adr/014-capability-resolution.md)); expose DuneOS as a Python module (`machine`-like shim over `/dev`). Replaces the need for a bespoke `awk`. No kernel change — it's just a big app. Not viable on the no-PSRAM CardPuter (GC heap wants ≥32-64 KiB; ~600 KiB-1.5 MiB of code); natural on the DevKitC reference board.
- **Flipper Zero (STM32WB55) board port** — assessed 2026-06-09. A third architecture (ARM Cortex-M4, ARMv7-M Thumb-2) running DuneOS *as the firmware* (flashed over SWD/DFU, replacing FuriOS — a product decision: loses the FAP ecosystem). Difficulty: **moderate-to-high but architecturally on-rails, especially after Phase 29 (RP2040)**, which already lands ARM toolchain, ARM Thumb ELF relocations (`loader_reloc_arm.c` — M0+ ARMv6-M vs M4 ARMv7-M overlap heavily), bare-metal bring-up without an ESP-IDF, and FreeRTOS-via-OSAL (Phase 26). The 256 KiB RAM (less than CardPuter's 320) makes the recent memory work (computed stacks [ADR 029], frugal config [ADR 030], handoff [ADR 031], the small arena) directly load-bearing. The genuinely new work: (1) STM32WB55 bare-metal bring-up — clocks/flash/RAM and especially the **USB stack** for shell/MSC, the heaviest piece; (2) the monochrome **1-bpp libgfx mode** (see Moderate-impact item — the Flipper display is ST7565 128×64, and our whole UI stack assumes RGB565); (3) per-chip userspace libs (`libst7565`, CC1101 sub-GHz, NFC/RFID/IR over `/dev/spi`,`/dev/i2c` — the native DuneOS model). Estimate post-Phase-29: a few weeks, dominated by (1) and (2), not a rewrite. No native WiFi (use the abstraction's "no backend", or the ESP32 WiFi devboard over UART).

## Moderate impact

- **App resource requirements: manifest `requires:` + generic `board.info` + launcher/dbt warning.** Let an app declare what it needs and warn (not silently fail/crash) when opened or flashed on an incompatible board — ADR-worthy, very aligned with the declarative model ([ADR 006](adr/006-manifest-extensibility.md) unknown-fields-ignored, [ADR 014](adr/014-capability-resolution.md), [ADR 024](adr/024-board-driven-responsive-views.md)). Shape: (1) manifest gains an extensible `requires:` block — `requires: { psram: true, min_heap: 131072 }` (stacks are already auto-sized, [ADR 029](adr/029-app-stack-auto-sizing.md), so `min_stack` is lower-value; `min_heap`/`psram` are the useful ones); (2) **`board.info`** — the generic, vendor-neutral board descriptor (not `CONFIG_SPIRAM`) — gains `psram: <bytes|0>` and `heap: <bytes>`, emitted by boardgen from `board.yaml`; (3) `libappmeta` exposes the `requires` fields (it already parses the manifest section); (4) the **launcher** compares `app.requires` vs `board.info` before launch and shows a warning dialog ("needs PSRAM — this board has none; run anyway?"), and **dbt** warns at `deploy`/`flashimg` time. Decentralised: each app declares its needs, a resolver checks — no central compatibility table. First real consumers: MicroPython ([ADR 035](adr/035-micropython-app.md)) and SSH (above), both `psram: true`.
- **Declarative per-app exit key (profile / `system` layer)** — today ESC=quit is a hardcoded cooperative convention baked into each GUI app (g_shell, future games call `duneos_exit(0)` on `KEY_ESC`). More elegant: declare the quit key *per app* in the profile / `dbt system` config — e.g. `exit_key: esc`, or none meaning "unquittable" — and have the kernel input layer enforce it (intercept the bound key → terminate the foreground app). This decouples the quit binding from both the app code *and* the board's available keys: a board with a different keymap (encoder, fewer buttons, touch) just ships a new profile, zero app rewrites. Depends on the supervisor force-kill + device-fd-reclaim path (see the device-fd-leak item under High impact) for safe termination, and on the input router tracking which app is foreground.
- **libgfx multi-display-format (1-bpp monochrome)** — surfaced 2026-06-09 from the Flipper Zero assessment (High impact). libgfx is RGB565-only today; every app and all of libui assume 16-bit colour. Small/low-power displays (Flipper's ST7565 128×64, many SSD1306/Sharp-memory panels, and likely some RP2040-class boards in Phase 29) are **1 bit per pixel**. Adding a monochrome backend touches libgfx broadly (colour→ink mapping, the canvas/blit/text paths, threshold for `GFX_RGB`), so it's worth **designing the abstraction during Phase 29** (when the first non-RGB target appears) rather than bolting it on per-board later. ADR 024 (responsive) already decouples layout from resolution; this decouples it from colour depth. Candidate for its own ADR ("display format abstraction") once a concrete second format lands.
- **libimage_png — full PNG decoder** — Phase 25.5 ships only the `.dr` raw RGB565 format (8-byte header + pixels), generated host-side by `dbt img convert`. That's enough for splash and app icons but doesn't help an app that wants to display arbitrary PNG/JPEG content from the SD card. If the need emerges, add `sdk/image/libimage_png.c` linking a minimal PNG decoder (e.g. `picopng`, ~3 KB, no zlib) for grayscale + RGB; full RGBA+IDAT needs zlib. JPEG: ESP-IDF already ships `jpeg_decoder` — could be re-exported as a kernel symbol. Userspace lib-per-format is the goal — libgfx stays mince.
- **App writable state** — Phase 25.5 standardised read-only config at `/etc/<app>/config.yaml` (provisioned by `dbt flashimg`). For state that the app *itself* writes (last brightness, recent files, prefs), we still have no API. Resolution direction chosen 2026-07-26: `/data/<app>/` on the new userdata partition (see High-impact `/data` item) + a `duneos_data_path()` libdune helper mirroring `duneos_config_path()`.
- **Control-plane ADR — bless the daemon IPC pattern before it fragments** — the first real daemon consumer (wifi, 2026-07-26) immediately converged on the trio: short command verbs over the supervisor mailbox (`SCAN`, `JOIN <arg>`) + binary state blobs in `/tmp/state/*` (ADR 027) + credentials/config in files (`/flash/etc`, soon `/data`). It works and it is Unix-shaped, but it is an oral convention. One short ADR ("daemon control-plane pattern") before battery/BLE/audio daemons each copy it divergently. Include the 64-byte mailbox payload limit and the "credentials never transit the mailbox" rule.
- **BL-ELF-EXTENT — the loader never checks that a section stays inside the file** — `duneos_elf_image_open()` validates the header and the section header table but no section extent, and `duneos_elf_io_t` carries no file size at all, so a `.dap` whose `sh_offset + sh_size` wraps past `UINT32_MAX` or simply runs past EOF is accepted and read at `loader.c:448`; closing it means extending `duneos_elf_io_t` with the image size and rejecting any section whose extent escapes it (covered on the bench today by the `sh_offset_size_overflow` expected failure in `tests/host/elf_corpus.c`, which cannot turn green without that API change).
- **BL-ELF-EMPTY-SYMTAB — a zero-size `.symtab` yields `symcount = 0` and `malloc(0)`** — nothing rejects a section header table that declares an empty symbol table, so `loader.c:1156` computes `symcount = 0` and allocates a zero-byte buffer whose return value is implementation-defined; the image is not refused up front by the validator with a named reject reason but only much later, when the `app_main` lookup loop at `loader.c:1277` never iterates and `loader.c:1293` reports `app_main not found in symbol table` — a diagnostic that says nothing about the malformed section header (covered on the bench by the `symtab_size_zero` expected failure in `tests/host/elf_corpus.c`, which needs either a new check in the pure unit or a probe reproducing the loader-side read).
- **Event bus / pub-sub** — current IPC is point-to-point via supervisor mailbox queues. Broadcast events (`battery_low`, `wifi_disconnected`, `usb_plugged`) would need a different mechanism. Defer until a concrete need emerges; not worth designing in the abstract.
- **Threat model: `/flash/bin` is writable by any FS_WRITE app** — a malicious/buggy `.dap` with `DUNEOS_PERM_FS_WRITE` can overwrite `/flash/bin/*.dap` and persist across reboots. Either state in ADR 011 that this is accepted (hacker device, physical access assumed), or gate writes under `/flash/bin` + `/flash/init.yaml` behind a dedicated permission bit. One-line decision, worth making explicitly.
- **Time-of-day / NTP-SNTP** — `clock_gettime(CLOCK_MONOTONIC)` works (it's the hardware timer); `CLOCK_REALTIME` returns whatever happens to be in the kernel's notion of wall clock (probably epoch). `wifi_daemon` doesn't do SNTP. Trivial to add once it matters; not blocking anything.
- **Kernel version exposure** — `DUNEOS_VERSION_STRING` is printed in klog at boot but isn't queryable at runtime. A `dbt info-device` that talks to the kernel over `/dev/ttyUSB0` would be useful for support ("what kernel are you running?"). Tiny scope; opportunistic.
- **`cd apps/user/<name> && python ../../../tools/dbt.py build`** is awkward after the `apps/system,user` split (one extra `../`). Either `dbt build <app_path>` from the repo root, or a `dbt` wrapper that walks up to find the repo root, would be cleaner. Tiny DX win.
- **Shell default cwd `/sd` is wrong when no SD is mounted** — `apps/system/shell_core/shell_core.c:31`, `shell_cmds.c:81` (`cd` no-arg), and `g_shell.c:56` all hardcode `/sd`. With SD absent, the user lands in a non-existent dir and `ls` returns ENOENT. Fix: at shell startup, `stat()` the mount points and fall back to `/flash` if `/sd` is missing — same logic for `cd` no-arg. Touches 3 files + a small helper.

## Low impact / niche

- **tmpfs is a flat namespace — no real directories** (`vfs_tmp.c`). `mkdir /tmp/a/b` doesn't create a traversable tree: files are stored by full flat name, so `opendir("/tmp/a")` yields entries like `a/b/file` (not `file`), `stat("/tmp/a")` on a "dir" fails, and `find`/glob/`test -d` can't walk a `/tmp` subtree (confirmed 2026-06-14 via the CLI self-test; the same ops on `/sd` FAT work). Flat files are fine (ambient `/tmp/state/*`, pipe scratch, redirects). Fix if/when something needs a `/tmp` hierarchy: give tmpfs real directory inodes + hierarchical readdir. Until then, scratch trees belong on `/sd` or `/flash`.

- **Atomics, rw-locks, barriers** in `libdune.a` — POSIX `<stdatomic.h>` would be cheap to add (PicoLibc has it ; libdune just needs to expose). `pthread_rwlock_*` and `pthread_barrier_*` similar. Add when a real caller asks.
- **Multi-file apps / dependencies** — every `.dap` is self-contained today. If a user wants to share `libfoo.c` across three apps, they `#include` it in each manifest's `sources:`. Linkage with shared libraries (Phase 33 "Shared Libraries `.dsl`" study) is the answer but the study hasn't started.
- **Filesystem features** — `fsync()` isn't exposed (data-integrity risk if a power-cut interrupts a write); no per-app quota (a buggy app can fill `/sd`); no symlinks even on LittleFS (it supports them, we don't expose). Each is a small standalone task.
- **i18n / keyboard layouts** — the keymap is hardcoded per board (CardPuter has French AZERTY in code today). Multiple layouts would mean a runtime-selectable keymap; not worth it until there are multiple users on different layouts.
- **ABI churn policy** — we've bumped to v3; every bump forces user apps to rebuild. No "stable ABI promise" beyond CLAUDE.md prose. Could formalise: "ABI is unstable until v1.0; until then expect a bump per phase that touches `duneos_api_t` layout." Tiny doc, not a phase.

## Out of scope / probably never

- **Video output (HDMI, MIPI-DSI)** — only ESP32-P4 has the hardware among current targets; Phase 30 (Audio) doesn't extend to video. Wait until a board demands it.
- **Hot reload / live code patching** — Linux doesn't do it ; DuneOS won't either. Apps that need to upgrade themselves call `duneos_restart()` after writing their new `.dap`.
- **Privilege separation via software MPU** — see [ADR 011](adr/011-threat-model.md). Cost/benefit doesn't work on these chips.
- **Container-like sandboxing** — same answer as above plus no `chroot` plumbing exists.
- **Distributed compute / mesh networking primitives** — well outside the manifesto's "Flipper / Playdate sweet spot". Apps that want it use the existing socket layer over WiFi.

## How to use this file

- **Adding an item:** write one sentence. If you can't say it in one sentence, it's two items in disguise.
- **Promoting an item:** when an item earns scheduling, move it out (to ROADMAP_v2.md or a new ADR) and delete the line here. The git history keeps the discussion.
- **Removing an item:** if it stops being relevant (e.g. solved by a different design choice), delete the line and add a one-line note in the commit message explaining why.
- **Linking to context:** if a backlog item connects to an existing ADR/Phase/file, link it inline. Don't expand here.
